# iPhone 原生 BLE 连接实验报告

归档日期：2026-09-07。本文是实验结论与证据报告，配套 [复现手册](docs/REPRODUCE.md)、[实现说明](docs/IMPLEMENTATION.md) 和 [结构化记录](results/observations.json)。各次实测的具体日期、iPhone 型号、iOS 版本及适配器型号未完整记录，不补造这些信息。

2026-09-08 增补 BZ-HID-05/06/07：HID 提供进程退出后的保持、重启后只读等待，以及临时提供 HID 建连后退出的结果与复现材料。

## 1. 明确结论

**在本次电脑、现有单只蓝牙适配器和 iPhone 上，消费控制类 HID over GATT 已通过短时连接验证；使用 BlueZ 提供 HID 时，可以同时保留原有蓝牙设备连接。**

| 问题 | 本次结论 | 依据 |
| --- | --- | --- |
| iPhone 只用系统功能能否连接？ | HID 路径可以。独占 HID 完成首次数字确认配对、加密和报告订阅；BlueZ 共存路径也完成配对与后续服务验证。 | EX-HID-01、BZ-HID-02、BZ-HID-04 |
| 首次配对后能否从电脑侧恢复，而不用每次操作手机？ | 独占模式已在锁屏条件下完成初始连接及三次断开后重连；共存默认模式也从无目标 LE 连接进入加密 HID 访问。 | EX-HID-03、BZ-HID-04 |
| 电脑是否整体变成 HID，导致其他蓝牙连接不可用？ | 共存模式是在原 BlueZ 身份上增加 HID 服务。本轮目标手机 LE 连接与一条原有 BR/EDR 连接同时保持 15 秒，原连接无中断。 | BZ-HID-04 |
| 会不会影响音乐和输入？ | 独占 HID 的 60 秒检查中，用户确认音乐和屏幕键盘正常；共存短测中用户确认音频未断。输入报告发送数均为 0。 | EX-HID-04、BZ-HID-04 |
| ANCS 或 CTS 是否也通过？ | 没有。当前单独服务征询配置未通过发现/连接，不能据此评价其他实现或全部 iOS 设备。 | EX-ANCS-01、EX-CTS-01 |
| 共存实验结束后能否恢复？ | BZ-HID-04 的设置、临时广播/HID、新增手机 LE 连接均恢复通过，原连接和配对属性保持。配对记录按设计保留。 | BZ-HID-04 |
| 维持已建立的连接必须常驻 HID 程序吗？ | 本轮不需要。提供进程正常退出且确认 HID/广播撤销后，同一既有加密 LE 保持 60.1 秒；连接按本项测试设计保留。 | BZ-HID-05 |
| 重启后不启动 HID，能否直接恢复连接？ | 本轮 20 秒内未观察到目标 LE；电脑配对记录仍在，没有进入保持观察。不能据此认定必须常驻 HID。 | BZ-HID-06 |
| 重启后临时提供 HID，建连后退出是否可行？ | 本轮从无目标 LE 建立唯一加密 LE；提供进程正常退出、HID/广播撤销后，同一连接保持 60 秒。 | BZ-HID-07 |

前期“从电脑侧恢复”实验的实际机制是电脑重新提供可连接广播，由 iPhone 作为 BLE 中央设备连回；**没有验证电脑主动扫描并向 iPhone 发起连接这一机制**。BZ-HID-05 从已有连接开始，不计作重连。脚本也不能独立确认手机是否锁屏：独占锁屏条件由用户明确确认，共存短测按锁屏且不操作手机的步骤执行后，用户反馈“一切正常”。

选择结论：**按需临时提供 HID 建立连接、完成后退出的路径已有短测依据，不能再以“维持已有连接”为由直接认定 HID 程序必须常驻。** BZ-HID-07 完成建连与退出后保持；与 BZ-HID-06 相比 Trusted 也从 false 变为 true，不能把恢复原因全部归于 HID。正式认证尚未接入，长期表现不由本次短测保证。

## 4. 关键成功证据

### 4.1 独占 HID：首配与使用影响

EX-HID-01 的首配结果包含 `bond_saved=true`、`encryption=true`、`report_subscribed=true`、`hold=true` 和 `passed=true`，保持配置为 30 秒。用户主动确认了数字配对。

EX-HID-04 复用同一实验身份，配置 60 秒保持，结果同样通过且 `reports_sent=0`。用户原话为“音乐和屏幕键盘输入都正常”。该轮允许操作手机以检查键盘，不能额外算成一次锁屏测试。

### 4.2 独占 HID：锁屏初始连接加三次重连

完整脱敏附件：[EX-HID-03.log](results/evidence/EX-HID-03.log)。命令使用 `--cycles 3 --hold-seconds 30 --initial-timeout 45 --reconnect-timeout 30`。

| 周期 | 含义 | `link_seconds` | `service_ready_seconds` | 加密/订阅/保持 |
| --- | --- | --- | --- | --- |
| 1 | 启动后的初始连接 | 0.007 | 0.573 | 均通过 |
| 2 | 第一次断开后重连 | 0.034 | 0.541 | 均通过 |
| 3 | 第二次断开后重连 | 0.035 | 0.542 | 均通过 |
| 4 | 第三次断开后重连 | 0.035 | 0.542 | 均通过 |

每轮保持 30 秒、输入报告发送数为 0；最终 `passed=true`，恢复 `settings_restored=true`。`link_seconds` 从开始广播计至收到连接；`service_ready_seconds` 从加密完成后的服务准备阶段开始计时，中间的加密等待没有独立耗时字段。因此**不能将任一字段或简单相加当作完整恢复总耗时**，也不能从这几个样本推出跨设备性能结论。

### 4.3 BlueZ 共存：完整通过

关键日志摘录：[BZ-HID-04.json](results/evidence/BZ-HID-04.json)。命令使用 `--wait-seconds 20 --hold-seconds 15`，不带 `--repair-phone-pairing`。

1. 开始时 `phone_le_connected=false`。
2. 出现目标手机 `link=LE`、`attribute=report_map` 的 `target_gatt_access`。
3. 出现 `service_ready`，`encrypted_phone_hid_access=true`。
4. 15 秒保持完成，`passed=true`、`original_links_preserved=true`、`original_links_lost=[]`。
5. 用户确认“一切正常，音频没有断”。

恢复结果为：`settings_restored=true`、`connections_restored=true`、`original_connections_present=true`、`pairing_properties_unchanged=true`；临时 HID 被移除，广播计数为 0，新增目标手机 LE 已断开，无待检查连接。

全局 Report 订阅有被观察到，但 `phone_hid_subscription_verified=false`：BlueZ 的订阅回调缺少设备归属，不能把它写成“已证明目标手机订阅”。`phone_audio_isolation_verified=false` 同样保留：本轮没有新增目标手机音频传输且人工体验正常，不代表所有音频服务都被隔离。

### 4.4 HID 服务撤销后：原加密 LE 保持

完整事件转录：[BZ-HID-05.json](results/evidence/BZ-HID-05.json)。命令使用 `hid_release_test.py --wait-seconds 20 --observe-seconds 60`，复现步骤和前期失败记录见 [HID_RELEASE.md](docs/HID_RELEASE.md)。

1. 注册前 `hid_uuid_present=false`、`advertising_instances=0`，已有唯一目标加密 LE；`Paired/Bonded=true`、`Trusted=false`、`Blocked=false`。
2. 在已有连接上注册 HID，完成 5 秒基线；本轮还观察到目标加密 HID 读取。
3. `provider_returncode=0`、`provider_dbus_closed=true`；随后确认 `hid_removed=true`、广播实例为 0。
4. 注销后同一 LE 持续加密，最终 `verdict=passed`、`observed_seconds=60.1`；未主动断开或修改配对。

本轮 `connection_setup=existing`，没有测量新建连接过程。手机锁屏是操作要求，脚本不能独立核实。用户此前反馈的断开后很快自动连回另行保留为人工观察，不能混入本轮连续保持的判据。

这个结果足以否定“维持这条已建立的连接必须让 HID 提供程序一直运行”的必要性判断。它不证明无限保持、电脑重启后恢复或一次 HID 配对即可永久替代服务。

### 4.5 临时 HID 建立连接，退出后继续保持

完整事件转录：[BZ-HID-07.json](results/evidence/BZ-HID-07.json)。按重启后临时提供 HID 的步骤运行，使用 `--wait-seconds 20 --observe-seconds 60`，手机锁屏、无需点击连接是操作要求，日志不能独立核实这些手机侧条件。

1. 初始没有 HID 或广播，目标 `Paired/Bonded/Trusted=true`、`Blocked=false`。
2. HID 和广播注册后，初始快照仍为 `phone_le_connected=false`、`hci_le_links=0`。
3. 随后 `connection_setup=automatic`，目标唯一 LE 已加密，进入 5 秒基线。
4. 提供进程退出码 0、D-Bus 关闭；确认 `hid_removed=true`、广播实例为 0。
5. 同一加密 LE 保持 60.0 秒，最终 `passed`，结束未主动断开连接。

本轮 `encrypted_hid_read_seen=false`，只能计为加密链路建立和保持成功，不能补写重新读取 HID 或目标订阅成功。日志没有独立建连耗时字段，不从进度输出间隔推导精确性能。

BZ-HID-06 的 Trusted 为 false，本轮在提供进程启动前已为 true，变更来源未记录。两轮不构成只改变 HID/广播的对照，不能判定 HID 是恢复的唯一原因，也不能判定 Trusted 为假导致上一轮未连接。这不影响 BZ-HID-07 对本轮建连、服务撤销及后续保持的直接证据。

因此，本次注册 HID 不能解释在注册前已出现的 Trusted=true；该字段是电脑对手机的信任标记，当前实验增减的是电脑提供的服务，没有因此切换电脑身份。详见 [身份与 Trusted](docs/HID_RELEASE.md#设备身份与-trusted)。已验证顺序为先建立加密连接、保持 5 秒基线，再退出 HID；“先退出服务再建立连接”以及省略基线后立即退出均未测量。

## 5. 失败和修订留下的结论

BZ-HID-06 的完整事件转录见 [BZ-HID-06.json](results/evidence/BZ-HID-06.json)。按电脑重启后只运行观察脚本的步骤，初始 HID UUID 不存在、广播实例为 0；`paired/bonded=true`、`trusted=false`。四次快照均为 `bluez_connected=false`、`phone_le_connected=false`、`hci_le_links=0`，20 秒后在 `connect` 阶段返回 `inconclusive`，观察接口正常关闭。

这轮没有 60 秒连接保持结果，但有“等待期内没有恢复连接”的实测价值。日志不能独立核实重启和手机锁屏条件，不能证明无限等待也不会恢复、必须常驻 HID，或 Trusted 为假就是原因。后续临时启动 HID 建立连接再退出已通过，单独记录为 BZ-HID-07，复现命令见 [HID_RELEASE.md](docs/HID_RELEASE.md#重启后临时启动-hid连接后退出)。

| 经验 | 正确解释 | 后续复现规则 |
| --- | --- | --- |
| 广播注册成功后手机仍不可见 | 只证明某个本机阶段成功，未证明手机收到或选择该服务 | 分别记录广告、连接、加密、服务、保持和恢复 |
| 名称放扫描响应曾被怀疑 | 成功的 BlueZ 路径同样使用扫描响应中的 `<COMPUTER_NAME>`，不能将这个位置认定为普遍失败原因 | 诊断只核对实际命令和字段，不凭名称位置判平台支持 |
| `hci0/hci1` 与 `<COMPUTER_NAME>` 混淆 | 前者是控制器编号，后者是手机可见名称；不是同一概念 | 明确传入控制器，名称按所选入口说明 |
| 同名列表项 | 同名不证明同一身份，也不证明两只物理适配器；早期两个 `<COMPUTER_NAME>` 未完成身份核验 | 不承诺通过改名控制 iOS 条目数量 |
| 不同候选之间是否要忘记配对 | 当前 Bumble 为每个模式分配不同身份；BlueZ 共存则使用原电脑身份 | 不为切换候选删除已通过 HID 的配对；不把 Bumble 配对当成 BlueZ 配对 |
| 旧手机配对被忽略后仍跑默认模式 | 电脑上的 Paired 属性不能证明手机仍保存密钥 | 首次/修复与复用命令分开说明，前提放在命令之前 |
| 修复模式重复运行 | 没有新数字确认时，当前实现不会放行 GATT 访问 | 配对完成后去掉修复参数；保留为 BZ-HID-03 的观测不足记录 |
| 低电量时曾失败 | 有失败日志和用户归因，没有受控实验 | 保留条件备注，不写成已证实根因，也不抹去后续成功 |
| 保持一会后自行退出 | 配置的周期和保持时间结束，脚本按设计清理 | 解释每阶段时限；`cycles=0` 表示零次额外重连，不表示无限运行 |
| 恢复 Busy | 可能处于 BlueZ 接回控制器的过渡期，本轮单独恢复最终通过 | 保留日志、有界重试，禁止删除恢复依据来掩盖失败 |
| 把 Paired/Bonded/Trusted 当作本项保持测试的门槛 | 通用配对属性不能证明 LE 就绪，Trusted 为假也不等于已建立链路未加密 | 本项直接核对精确目标 LE、加密和连续性；不擅自修改信任设置 |
| 要求先断开再抢时间运行 | 已有连接可以直接作为注销观察起点 | 标记 `connection_setup=existing`，不将其计作新建或重连 |
| HID 提供进程退出报错 | 关闭 D-Bus 后再 unexport 的顺序在真实私有总线上复现 errno=9；纯假后端未覆盖 | 关闭并等待 D-Bus 完成；实际核对进程退出码、总线身份及服务撤销 |

## 6. 尚未证明的事项

- 长时间保持、真实走远后返回、电脑睡眠、iPhone 重启、不同 iOS/硬件的表现。
- 重启后恢复路径在重复运行及其他环境中的表现；Trusted 条件一致时，只改变 HID/广播对恢复的影响。
- 所有音频配置文件的隔离，及共存模式下所有输入场景的兼容性。
- 电脑主动作为 BLE 中央设备连入 iPhone 的可用性。
- 正式认证安全、距离判定精度、RSSI 阈值、抗冒用能力及系统认证接入。
- 手机内部缓存、系统日志、外部进程状态可被实验脚本完全回滚。

这些项目尚未验证。评估其他环境或正式认证接入时，应另行确定验证范围。
